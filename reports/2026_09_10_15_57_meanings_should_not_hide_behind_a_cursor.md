# 뜻은 커서 뒤에 숨을 필요가 없다

## 예문 전체를 링크로 만드는 대신 독일어와 문맥 뜻을 위아래로 짝짓는다. 이미 번역한 6,417문장을 다시 번역하지 않고, 모델은 경계와 짧은 뜻만 쓴다

2026년 9월 10일 오후 3시 57분 | 12 min read

*Ab morgen muss ich arbeiten.* 앱은 이 문장을 꽤 영리하게 다뤘다. *morgen*을 누르면 *morgen* 카드가 열리고, *muss*를 누르면 사전에 적힌 기본형 *müssen*으로 간다. 화면에 적힌 것은 문장이지만 그 아래에는 단어장이 숨어 있다.

문제는 그 영리함이 학습자에게 보이지 않았다는 데 있다. 뜻은 커서를 올려야 검은 말풍선으로 나타났고, 휴대폰에서는 첫 번째 탭이 뜻을 열고 두 번째 탭이 이동했다. 읽기 위해 눈을 쓰던 사람이 뜻을 확인하려고 손을 움직여야 했다. 한 문장 안에서 이 일을 다섯 번 하면 예문은 더 이상 문장이 아니다. 조그만 링크 다섯 개가 된다.

말풍선은 이미 걷어 냈다. 그러나 검은색을 지운 것은 증상을 지운 것이지 문제를 푼 것은 아니다. 이제 단어는 눌리지만 뜻은 보이지 않는다. 다음 화면은 링크를 덜 요란하게 만드는 데서 그쳐서는 안 된다. 독일어와 뜻을 처음부터 같은 자리에 놓아야 한다.

```
Ab        morgen       muss          ich       arbeiten.
~부터     내일          ~해야 한다     나는      일하다

```

이 형식을 행간 주석(interlinear gloss)이라고 부른다. 이름보다 중요한 것은 읽는 순서다. 눈은 *morgen*에서 아래로 한 번 내려가 “내일”을 보고, 다시 다음 독일어로 간다. 커서도, 말풍선도, 기억해야 할 임시 상태도 없다. 구현 단계에서 내린 최종 결정에 따라 이 주석이 있는 예문은 기존 전체 한국어·영어 번역을 화면에서 숨긴다. 둘을 함께 보이면 같은 뜻이 중복되어 새 레이아웃의 초점이 흐려지기 때문이다.

## 지금 앱은 단어를 찾을 뿐, 뜻을 번역하지 않는다

현재 `Examples.svelte`는 문장을 `sentenceParts()`에 보낸다. 이 함수는 독일어처럼 생긴 문자열을 정규식으로 하나씩 자르고, 표제어나 명시된 활용형과 같은 표면형을 찾아 단어 id를 붙인다.

```ts
const WORD_RE = /[A-Za-zÄÖÜäöüß]+/g;

export function sentenceParts(text: string, currentId: string, surfaces: Map<string, string>) {
  const parts = [];
  let at = 0;
  for (const match of text.matchAll(WORD_RE)) {
    const index = match.index ?? 0;
    if (index > at) parts.push({ text: text.slice(at, index) });
    const wordId = surfaces.get(match[0].toLowerCase());
    parts.push({ text: match[0], wordId, current: wordId === currentId });
    at = index + match[0].length;
  }
  if (at < text.length) parts.push({ text: text.slice(at) });
  return parts;
}
```

이 장치는 *muss*가 *müssen*으로 간다는 사실은 안다. *muss*가 이 문장에서 “~해야 한다”라는 사실은 모른다. 예전에 말풍선이 보여 준 것도 문맥 뜻이 아니라 단어 카드의 `ko`였다. 여러 뜻을 가진 단어라면 예문에 쓰이지 않은 뜻까지 쉼표 뒤에 따라왔다.

서로 다른 한국어 세 가지를 먼저 구별해야 한다.

| 이름 | 예 | 하는 일 |
|---|---|---|
| 사전 뜻 | `müssen → ~해야 한다` | 단어 카드에 한 번 저장한다 |
| 문맥 주석 | `muss → ~해야 한다` | 예문 속 표현 바로 아래에 놓는다 |
| 문장 번역 | `내일부터 일해야 해요.` | 주석 생성의 기준으로 쓰고, 주석 적용 뒤에는 화면에서 숨긴다 |

사전 뜻을 그대로 복사하면 값은 싸지만 자주 부정확하다. 문장 번역을 낱말 수만큼 잘라 놓으면 한국어 어순 때문에 무너진다. 새로 필요한 것은 둘 사이에 있는 문맥 주석이다. 짧아야 하고, 원문의 어느 범위를 설명하는지도 알아야 한다.

## 한 단어씩만 자르면 독일어도 틀리게 가르친다

모든 칸을 한 단어로 고정하고 싶은 유혹이 있다. 구현하기 쉽고 표도 반듯하다. 그러나 *Wie geht es Ihnen?*을 `Wie/어떻게`, `geht/가다`, `es/그것`, `Ihnen/당신에게`로 놓으면 각 칸은 사전적으로 그럴듯하고 문장 전체는 거짓말이 된다. 학습자가 알아야 할 것은 `Wie / geht es / Ihnen?`와 `어떻게 / 지내세요 / 선생님은?`에 가깝다.

따라서 화면의 기본 단위는 낱말이 아니라 **한 개 이상의 연속된 독일어 낱말과 한 개의 한국어 뜻 조각**이다. 대부분은 하나 대 하나이고, 숙어나 문법 구조만 둘 이상을 묶는다.

```
Ab | morgen | muss       | ich  | arbeiten.
1  | 1      | 1          | 1    | 1
~부터 | 내일 | ~해야 한다 | 나는 | 일하다

Wie | geht es  | Ihnen?
1   | 2        | 1
어떻게 | 지내세요 | 선생님은?
```

위의 가운데 숫자는 화면에 보여 줄 것이 아니다. 모델과 파이프라인이 표현의 경계를 주고받는 가장 싼 방법이다.

## 번역을 시키지 말고 경계만 세게 한다

데이터 공장에는 이미 6,417개의 자연스러운 한국어 문장 번역이 있다. A1 2,585개, A2 1,639개, B1 2,193개다. 독일어 낱말은 모두 합쳐 44,498개이고 문장당 평균 6.93개다. 새 기능을 만든다고 이 문장을 다시 번역하는 것은 돈을 두 번 내고, 기존 번역과 새 주석이 서로 다른 해석을 갖게 만드는 일이다.

모델에 보내야 할 것은 세 가지뿐이다.

```
s42f...\tAb morgen muss ich arbeiten.\t내일부터 일해야 해요.
```

id, 독일어 원문, 이미 검수할 대상으로 삼은 한국어 번역이다. 영어 번역과 등급, 단어 카드 전체, 품사와 발음은 보내지 않는다. 영어는 앞 단계가 한국어 문장을 만들 때 이미 쓰였다. 등급은 문장을 정렬하는 데 아무 역할을 하지 않는다.

돌아오는 답도 독일어를 되풀이하지 않는다.

```json
{
  "items": [
    {
      "id": "s42f...",
      "g": [[1, "~부터"], [1, "내일"], [1, "~해야 한다"], [1, "나는"], [1, "일하다"]]
    }
  ]
}
```

`[1, "내일"]`은 “아직 쓰지 않은 독일어 낱말 하나를 소비하고 그 아래에 `내일`을 둔다”는 뜻이다. `[2, "지내세요"]`는 두 낱말을 한 묶음으로 만든다. 독일어 원문과 구두점은 프로그램이 이미 갖고 있으므로 응답에 다시 쓸 필요가 없다. `de`, `ko`, `wordId` 같은 키를 모든 조각마다 반복할 필요도 없다.

이 압축은 단지 비용을 위한 잔재주가 아니다. 모델이 독일어 철자를 고치거나 구두점을 빼거나 같은 문장을 조금 다르게 돌려주는 실패를 구조적으로 없앤다. 모델은 경계의 길이와 짧은 뜻만 결정한다. 원문을 소유하는 쪽은 계속 데이터셋이다.

## 앞 보고서가 아낀 토큰을 다시 아끼는 법

이 프로젝트는 예문 번역 비용을 이미 한 번 줄였다. 60문장 탐침에서 기본 설정은 116초와 출력 12,029토큰을 썼다. 도구를 끄고 effort를 낮추자 31.9초와 2,491토큰이 됐다. 처음에는 번역 말투가 흔들렸지만, 원인은 싼 설정이 아니라 “주어가 ich인 평서문은 어떤 말투로 옮기는가”가 비어 있던 프롬프트였다. 규칙을 채운 뒤 같은 낮은 effort로 품질을 되찾았다.

새 단계도 같은 장치를 그대로 쓴다.

| 장치 | 예문 번역에서 한 일 | 문맥 주석에서 할 일 |
|---|---|---|
| 도구 끄기 | 3만 토큰짜리 일반 시스템 프롬프트와 도구를 떼었다 | `llm.py`의 `--tools ""`를 그대로 쓴다 |
| 낮은 effort | 짧고 좁은 번역에 과한 추론을 쓰지 않았다 | 경계와 짧은 뜻만 요구한다 |
| 묶음 처리 | 문장 60개를 한 요청에 보냈다 | 출력이 더 길므로 20·40·60개를 재서 정한다 |
| 좁은 스키마 | 설명 대신 `id`, `ko`만 받았다 | `id`, `g`만 받는다 |
| 중단 후 재개 | 이미 쓴 id를 건너뛰었다 | `gloss_draft.jsonl`의 id를 건너뛴다 |
| 낮은 등급부터 | A1을 먼저 만들고 검수했다 | A1 2,585문장부터 공개한다 |

한 가지는 그대로 복사하지 않는다. 번역은 문장 하나당 출력 한 줄이면 끝났지만 주석은 평균 여섯 조각 안팎을 낸다. 그러므로 “지난번에 60개였으니 이번에도 60개”라고 정하지 않는다. A1에서 대표 문장 60개를 뽑아 묶음 크기 20, 40, 60을 시험하고, 잘림 없이 가장 큰 값을 고른다. 측정할 것은 시간과 가격만이 아니다.

1. 조각의 숫자를 더했을 때 독일어 낱말 수와 정확히 같은가.
2. 한국어가 빈 조각이 있는가.
3. 숙어를 한 단어씩 잘라 뜻을 망쳤는가.
4. 기존 자연 번역과 뜻이 충돌하는가.
5. 설명문이나 대안을 괄호에 늘어놓았는가.

비용은 이 60문장 탐침 뒤에야 적는다. 아직 호출하지 않은 모델의 달러 값을 보고서에 미리 쓰는 것은 측정이 아니라 소망이다. 확실히 말할 수 있는 상한은 따로 있다. 전체 데이터에는 독일어 낱말이 44,498개 있으므로 주석 조각은 그보다 많을 수 없고, 여러 낱말 표현을 묶을수록 줄어든다. A1의 상한은 16,422조각이다.

## 프롬프트는 비싼 모델의 눈치를 보지 않게 써야 한다

낮은 effort에서도 흔들리지 않게 하려면 모델이 스스로 문체와 목적을 추측할 일이 없어야 한다. 시스템 프롬프트의 핵심은 아래 정도다.

```text
너는 A1~B1 독일어 예문에 행간 한국어 주석을 다는 편집자다.
입력은 id, 독일어 원문, 자연스러운 한국어 번역이다.

- 독일어의 모든 낱말을 원래 순서대로 정확히 한 번 소비한다.
- 각 g 항목은 [연속된 낱말 수, 그 범위의 문맥상 한국어 뜻]이다.
- 보통 한 낱말씩 두되, 숙어·분리동사·문법 표현은 뜻이 깨지지 않을 만큼 묶는다.
- 뜻은 사전식으로 짧게 쓴다. 문장 종결, 해설, 괄호 속 대안은 쓰지 않는다.
- 조사와 어미는 이해에 필요할 때 붙인다. 자연 번역과 의미가 충돌해서는 안 된다.
- 독일어 원문과 전체 한국어 번역을 출력에 되풀이하지 않는다.
- 출력은 스키마에 맞는 JSON만 쓰고 id를 빼거나 더하지 않는다.
```

여기서 “직역하라”라고만 쓰지 않는 것이 중요하다. *muss* 아래의 “해야”는 좋지만, 모든 대명사 아래에 한국어 조사를 억지로 배분하면 문장이 더 어려워진다. 목표는 독일어 어순을 보존한 자연스러운 번역이 아니라, 독일어 표현을 이해시키는 짧은 표지다. 기존 자연 번역은 이 주석을 만드는 기준 데이터로 남는다.

## 검증은 모델보다 싸고 엄격하다

출력 스키마는 작게 만든다.

```python
class GlossItem(BaseModel):
    model_config = ConfigDict(extra="forbid")
    id: str
    g: list[tuple[int, str]]

class GlossBatch(BaseModel):
    model_config = ConfigDict(extra="forbid")
    items: list[GlossItem]
```

스키마가 JSON의 모양을 보장하면 프로그램은 내용을 검사한다. `sum(span)`이 원문의 낱말 수와 다르면 저장하지 않는다. span이 1보다 작거나, 뜻이 비었거나, 뜻이 지나치게 길거나, 독일어 원문을 그대로 복사했어도 실패다. 실패한 id만 한 번 더 보내고, 그래도 실패하면 다음 실행을 위해 남긴다. 이미 `llm.py`가 누락 항목 수집, 병렬 묶음, 한 차례 재시도, 모델 이름 기록을 담당하므로 새 호출 장치는 만들지 않는다.

정상 응답은 `data/gloss_draft.jsonl`에 즉시 이어 쓴다.

```json
{"id":"s42f...","g":[[1,"~부터"],[1,"내일"],[1,"~해야 한다"],[1,"나는"],[1,"일하다"]],"model":"sonnet","v":1}
```

`v`는 프롬프트와 데이터 형식의 버전이다. 나중에 규칙이 바뀌어도 모든 결과를 막연히 다시 만드는 대신 이전 버전만 골라 재생성할 수 있다. 사람이 고친 결과는 `gloss_overrides.jsonl`에 같은 id로 쓴다. 생성 초안을 직접 고치지 않는다는 현재 `overrides.tsv`의 원칙을 중첩 데이터에도 이어 가는 것이다.

자동 검증을 통과했다고 좋은 주석은 아니다. 사람에게는 전부가 아니라 의심할 이유가 있는 문장부터 보여 준다.

- 두 낱말 이상을 한 조각으로 묶은 문장
- 뜻 하나가 15자를 넘는 문장
- `nicht`, `kein`, `nur` 같은 범위 표현이 홀로 떨어진 문장
- 분리동사의 두 부분이 서로 다른 조각에 있는 문장
- 같은 독일어 표면형이 여러 문장에서 크게 다른 뜻을 얻은 경우

이 목록은 `gloss_review_queue.tsv`가 된다. 전체 A1도 한 차례 읽어야 하지만, 위험한 문장을 먼저 고치면 앱을 시험하는 동안 보게 될 큰 오류부터 사라진다.

## 화면에서는 쌍이 줄바꿈의 최소 단위다

최종 `sentences.json`에는 자연 번역과 압축된 주석이 함께 들어간다.

```json
{
  "id": "s42f...",
  "de": "Ab morgen muss ich arbeiten.",
  "ko": "내일부터 일해야 해요.",
  "g": [[1, "~부터"], [1, "내일"], [1, "~해야 한다"], [1, "나는"], [1, "일하다"]]
}
```

브라우저는 기존 `WORD_RE`로 원문의 낱말 위치를 다시 찾고 `g`의 숫자만큼 묶는다. 공백은 조각 사이에 놓고 마침표와 쉼표는 앞 조각에 붙인다. 각 조각은 위에 독일어, 아래에 한국어를 둔 작은 두 줄짜리 열이다. 열들은 문장처럼 왼쪽에서 오른쪽으로 흐르다가 화면 끝에서 통째로 다음 줄로 내려간다.

```css
.ex-gloss-line {
  display: flex;
  flex-wrap: wrap;
  align-items: start;
  gap: 8px 10px;
}

.ex-gloss-pair {
  display: inline-grid;
  grid-template-rows: auto auto;
  justify-items: start;
  white-space: nowrap;
}
```

한 쌍 안에서는 줄바꿈하지 않는다. 그래야 화면 오른쪽 끝의 *arbeiten*과 다음 줄 왼쪽의 “일하다”가 헤어지지 않는다. 한국어 뜻은 독일어보다 작고 흐리게 두되, hover 색과는 관계없이 항상 읽을 수 있어야 한다.

링크는 없애지 않는다. 한 조각의 위쪽 독일어 안에서 현재 `sentenceParts()`가 알아보는 낱말만 눌리게 한다. 조각 전체를 링크로 만들면 `geht es`처럼 두 단어를 묶었을 때 어디로 이동할지 다시 모호해진다. 링크를 못 찾은 활용형은 평문으로 남는다. 불확실한 단어를 자신 있게 잘못 연결하는 것보다 낫다.

설정의 “예문 뜻은 눌러야 보인다”는 “예문 풀이를 눌러야 보인다”로 이름을 바꾼다. 이 설정을 켠 경우 문맥 주석을 가리고 한 번 누르면 연다. 주석이 적용된 예문의 기존 전체 한국어·영어 번역은 설정과 관계없이 표시하지 않는다.

## 데이터가 없는 동안 망가지지 않는 길

6,417문장을 모두 만든 다음에야 화면을 바꾸면 데이터와 UI의 오류가 한꺼번에 나타난다. 순서를 나눈다.

1. 하드코딩한 대표 예문 다섯 개로 두 줄 레이아웃을 먼저 만든다. 짧은 문장, 긴 문장, 구두점, 두 단어 묶음, 긴 한국어 뜻을 하나씩 넣고 320px 화면에서 본다.
2. A1 대표 60문장으로 묶음 크기와 프롬프트를 측정한다. 시간, 입·출력 토큰, 비용, 자동 검증 실패율, 사람 검수 오류를 표로 남긴다.
3. `05_glosses.py`를 만들고 A1 2,585문장만 생성한다. 기존 `llm.py`를 호출하고 결과를 id별로 누적한다.
4. merge 단계가 override를 우선해 `g`를 넣게 한다. `g`가 없는 문장은 지금처럼 일반 독일어 문장과 자연 번역만 보여 준다.
5. `Examples.svelte`를 두 줄 쌍 레이아웃으로 바꾸고 링크, 현재 단어 강조, 뜻 가리기 설정을 붙인다.
6. A1을 실제 휴대폰에서 읽은 뒤 A2와 B1을 순서대로 만든다.

새 단계를 5번으로 넣으면 현재 `05_merge.py`, `06_audio.py`, `07_site.py`는 한 칸씩 밀린다. 번호를 중복시키거나 `04b`를 만드는 것보다 한 번 이름을 고치고 Makefile과 README를 함께 고치는 편이 낫다. 데이터와 오디오는 안정된 id로 연결되므로 파일 번호가 바뀌어도 다시 생성할 필요가 없다.

주석이 없는 문장의 fallback이 중요하다. 배포 도중 일부 결과가 빠져도 화면이 비거나 예문이 사라져서는 안 된다.

```
g 있음  → 독일어/문맥 뜻 쌍. 기존 전체 한국어·영어 번역은 숨김
g 없음  → 기존 독일어 문장 + 자연 번역
```

## 성공은 말풍선이 사라진 것으로 재지 않는다

완료 조건은 다음과 같다.

| 항목 | 합격선 |
|---|---|
| 원문 보존 | 모든 주석의 span 합이 독일어 낱말 수와 일치 |
| 데이터 완결성 | A1 2,585문장에 유효한 `g`, 누락 0 |
| 조작 | hover 없이 뜻을 읽고, 독일어 낱말은 한 번 눌러 상세로 이동 |
| 모바일 | 320px에서 독일어와 그 뜻이 서로 다른 줄로 찢어지지 않음 |
| 의미 | 60문장 표본에서 치명적인 오역과 잘못된 묶음 0, 수정 사유 기록 |
| 호환 | `g`가 없는 문장도 지금과 같은 내용으로 표시 |
| 회귀 | 타입 검사, 단위 테스트, 프로덕션 빌드 통과 |

“치명적인 오류 0”은 모든 표현이 완벽하게 예쁘다는 뜻이 아니다. 부정 범위를 뒤집거나 숙어를 단어 뜻으로 해체하거나 다른 단어에 뜻을 붙이는 오류가 없어야 한다는 뜻이다. 어색하지만 이해 가능한 표현은 override 목록으로 고치면서 프롬프트의 다음 버전에 반영한다.

## 예문은 사전으로 가는 복도가 아니다

현재 설계는 예문을 여러 단어 카드로 가는 복도로 쓴다. 그래서 화면의 모든 단어가 문장보다 링크로 먼저 행동했다. 새 설계는 순서를 되돌린다. 예문은 먼저 읽고 이해하는 학습 자료다. 단어 상세는 필요할 때 갈 수 있는 두 번째 층이다.

이 변화에 거대한 번역 작업은 필요하지 않다. 자연스러운 한국어 6,417문장은 이미 있다. 모델에 다시 문장을 쓰게 하지 않고, 그 번역이 독일어의 어느 연속된 낱말에 대응하는지만 짧게 적게 하면 된다. 입력에서 필요 없는 영어와 등급을 빼고, 출력에서 독일어와 반복 키를 빼며, 도구와 높은 effort를 끈다. 사람은 모델이 쓴 모든 토큰을 믿는 대신 프로그램이 셀 수 있는 것은 프로그램으로 검사한다.

검은 말풍선을 없앤 자리에 빈칸을 남길 이유가 없다. 뜻은 단어 바로 아래에 있을 때 가장 적게 방해하고, 가장 빨리 읽히며, 가장 적은 조작을 요구한다. 그리고 뜻을 그 자리에 놓는 데이터도 생각보다 작게 만들 수 있다. ■
